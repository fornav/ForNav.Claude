# FORNAV AL report integration

Helps AL developers write and edit FORNAV report AL files, feed custom data into FORNAV report layouts, hook into FORNAV's report/email/e-invoicing events, and review existing integration code for common mistakes. FORNAV is a report-layout-designer product for Business Central; this skill covers the AL side, not the Designer UI.

## Report AL file structure

### Declaring the layout

A current FORNAV report declares a `Custom` rendering layout pointing at a `.docx` file, with `MimeType = 'FORNAV'`:

```al
Report 56789 "ForNAV Latest"
{
    DefaultRenderingLayout = FORNAV;
    ...
    rendering
    {
        layout(FORNAV)
        {
            Type = Custom;
            MimeType = 'FORNAV';
            LayoutFile = './Layouts/ForNAVLatest.docx';
        }
    }
}
```

The `MimeType = 'FORNAV'` tag is what routes rendering through FORNAV's report service instead of BC's native Word renderer. The `.docx` file is a real zip/Open XML file but its visible body is blank — the actual design is stored in `docProps/custom.xml` inside the zip (properties: `Document`, `DataContract`, `Json`). A file without those properties fails FORNAV's validation and is rejected.

Standard reports in FORNAV's own Customizable Report Pack use a `#if CUSTOM`/`#else` split (also declaring `WordLayout` for older BC versions). A new report you build yourself doesn't need that conditional — just use the `Custom` rendering declaration directly.

### Autogenerated code — do not touch

Every Designer save regenerates sections of the AL file marked with:

```al
// --> Reports ForNAV Autogenerated code - do not delete or modify
...
// Reports ForNAV Autogenerated code - do not delete or modify -->
```

and individual lines like:

```al
column(ReportForNavId_2; 2) { } // Autogenerated by ForNav - Do not delete
column(ReportForNav_Header; ReportForNavWriteDataItem('Header', Header)) { }
```

These include the `ReportForNav` codeunit variable declaration, `ReportsForNavInit()`, `ReportForNavWriteDataItem(...)`, and one serialization column per data item. Editing them is pointless — the next Designer save overwrites them.

### What you can safely edit

Everything **outside** the autogenerated markers is yours:

- Helper procedures (`ChangeLanguage`, `GetVatAmountLines`, `PrintLogo`, etc.)
- `OnInitReport`, `OnPreReport`, `OnPostReport` trigger bodies — as long as the generated init/pre calls inside them (`ReportsForNavInit()`, `ReportsForNavPre()`) stay in place
- The `requestpage` — its own fields, options, and validation logic
- Ordinary dataset mechanics on data items you own: `RequestFilterFields`, `DataItemTableView`, `CalcFields`, filters in `OnPreDataItem`

### Changing the dataset — Designer round-trip required

If you add or remove a data item, or add or remove a field the layout needs to display, you must **open and save the report in the FORNAV Designer** afterward — even if the AL change compiles and runs. The Designer regenerates `ReportForNavWriteDataItem` columns and rewrites the embedded `DataContract` JSON inside the `.docx` to match. Without that resave, the layout's contract is out of sync with the AL columns and the field shows as missing or is silently skipped.

### Adding a request page option

Request page fields are ordinary AL — nothing is autogenerated here:

```al
var
    NoOfCopies: Integer;

requestpage
{
    SaveValues = true;
    layout
    {
        area(Content)
        {
            group(Options)
            {
                Caption = 'Options';
                field(NoOfCopies; NoOfCopies)
                {
                    ApplicationArea = All;
                    Caption = 'No. of Copies';
                }
            }
        }
    }
}
```

A request page value only becomes available to the *layout* if it's also exposed as a non-autogenerated dataset column on the relevant data item:

```al
column(NoofCopies; NoOfCopies)
{
    IncludeCaption = false;
}
```

Once the column exists, the Designer exposes it as `DynamicsNavDataSet.<ColumnName>` in the layout. This new column still requires a Designer resave before the layout can bind to it.

### Shipping multiple built-in layouts

Declare several named layouts in the `rendering` block, each pointing at its own `.docx`:

```al
rendering
{
    layout(FORNAV)
    {
        Type = Custom;
        MimeType = 'FORNAV';
        LayoutFile = './Layouts/ForNAVLatest.docx';
    }
    layout(FORNAV2)
    {
        Type = Custom;
        MimeType = 'FORNAV';
        LayoutFile = './Layouts/ForNAVLatest-2.docx';
    }
}
```

`DefaultRenderingLayout = FORNAV;` picks the default; the others become additional selectable built-in layout choices. Each `.docx` is designed independently in the FORNAV Designer with its own `DataContract`/`Json`. This is distinct from custom layouts (stored in the BC database per company) — these ship compiled into the extension.

## Report extensions

A `reportextension` lets you add to an existing FORNAV report — a new column, a request page field, or an additional built-in layout — without touching the base report's AL object or its existing layout files.

### Adding a column — only needed for computed values

Unlike a standard AL/RDLC report, FORNAV does not need every field to be serialized into
the dataset as a column. FORNAV queries the underlying table **directly** at render time,
so a plain database field — whether it's a standard field that's always been on the table,
or one you added via a `tableextension` — is already available to the layout with no
`reportextension` column and no AL change at all. Bind to it in the Designer by the field
name, same as any other field on that DataItem's table.

Only add a `reportextension` column when the value **doesn't already exist as a field** —
it has to be computed, looked up, or assembled in AL (string formatting, a flowfield-style
calculation, concatenation, etc.):

```al
reportextension 50000 "PTE ForNAV VAT Sales Invoice" extends "ForNAV VAT Sales Invoice"
{
    dataset
    {
        add(Header)
        {
            column(PTECustomText; PTECustomText)
            {
                Caption = 'Custom Text';
            }
        }
    }

    var
        PTECustomText: Text;
}
```

`add(Header)` adds a column to the existing `Header` data item — standard AL report-extension syntax.

### Adding a request page field

```al
requestpage
{
    layout
    {
        addlast(Content)
        {
            field(PTECustomText; PTECustomText)
            {
                ApplicationArea = All;
                Caption = 'Custom Text';
            }
        }
    }
}
```

`addlast(Content)` appends the field to the base report's existing options group.

### Adding an additional layout

```al
rendering
{
    layout(ExtensionLayout)
    {
        Type = Custom;
        MimeType = 'FORNAV';
        LayoutFile = './Layouts/ForNAVVatSalesInvoice-ext.docx';
    }
}
```

This ships as an additional built-in layout alongside whatever the base report already declares, without modifying the base object or its `.docx` files.

### What you cannot do: add data items

A report extension can add columns to an *existing* data item and can add request page fields — it cannot declare a new data item. If the extension needs data the base report doesn't iterate, use FORNAV's **virtual DataItem** feature: add the DataItem directly in the FORNAV Designer layout rather than in AL. FORNAV treats a DataItem as virtual automatically when it can't find a matching AL declaration — which is always the case for report extensions.

### Using an extension column in the layout

Extension columns **do not appear in the FORNAV Designer's field list**. The field list is generated from the report's embedded `DataContract`, and that contract reflects only the base report's AL — there is nothing for the Designer to pick from a dropdown.

The data is still there at render time: the extension column is a real AL report column and gets serialized the same as any other. Bind to it by typing the source expression directly into the control's properties:

```
DynamicsNavDataSet.PTECustomText
```

This is the same `DynamicsNavDataSet.<ColumnName>` form used for any plain dataset column — you just have to type it rather than pick it from a list. The Designer resave rule still applies for the base report's own columns, but there is no Designer step to take for extension columns specifically — they arrive at render time regardless.

## Which approach — event subscriber or direct AL?

| | Event subscriber on `OnFillTemporaryTable` | Direct AL (`UseTemporary` in your own report) |
|---|---|---|
| Requires modifying the report object | No | Yes |
| Works against reports you don't own (e.g. standard FORNAV reports) | Yes — layout drives it | No |
| Configured from | FORNAV Designer: mark the DataItem/Record `Temporary` (+ `AutoPopulate` for DataItems) | The report's AL dataset |

Default to the event-subscriber approach unless you own the report object and have a reason to hardcode the temp DataItem into it.

## Recommended pattern: `OnFillTemporaryTable` event subscriber

`Codeunit::"ForNAV TempTable"` exposes the integration point. Verified directly against `Core/TempTable.Codeunit.al` in the FORNAV Report Pack source — there are **three** events on this codeunit, only one of which is for you:

| Event | Status | Use it? |
|---|---|---|
| `OnFillTemporaryTable` | Public `[IntegrationEvent]`, has `IsHandled` | **Yes — this is the one.** |
| `OnForNAVFillTemporaryTableForNAV` | `[Obsolete]` since FORNAV 8.2 | **No.** Some older KB articles still show this — they're wrong for current versions. |
| `OnFillTemporaryTableInternal` | `[InternalEvent]`, private to the Report Pack | **No — not subscribable from outside the extension.** FORNAV's own built-in subscribers use this. |

If you're working against an unfamiliar FORNAV version, grep the installed app's source (or decompiled symbols) for `Codeunit::"ForNAV TempTable"` to confirm this hasn't changed before relying on it — events do get deprecated across versions, as happened here.

### Signature

```al
[EventSubscriber(ObjectType::CodeUnit, Codeunit::"ForNAV TempTable",
    'OnFillTemporaryTable', '', false, false)]
local procedure MySubscriber(ReportID: Integer; ChildDataItemId: Text;
    ParentRecRef: RecordRef; var TempRecRef: RecordRef; var IsHandled: Boolean)
```

| Parameter | Description |
|---|---|
| `ReportID` | The report object number being rendered. |
| `ChildDataItemId` | Name of the DataItem in the layout. |
| `ParentRecRef` | The parent/sibling DataItem record — `SetTable()` to cast to a typed record. |
| `TempRecRef` | The temp table to fill — check `TempRecRef.Number` to identify it, `SetTable()` to cast, fill, then `Copy()` back. |
| `IsHandled` | Set `true` once you've handled it — stops other subscribers (and FORNAV's internal ones) from also running. |

### Worked example

```al
table 50100 "PTE Item Totals"
{
    DataClassification = SystemMetadata;
    TableType = Temporary;

    fields
    {
        field(1; "Item No."; Code[20]) { DataClassification = SystemMetadata; }
        field(2; Quantity; Decimal) { DataClassification = SystemMetadata; }
    }

    keys
    {
        key(Key1; "Item No.") { Clustered = true; }
    }

    procedure GetFromSalesHeader(SalesHeader: Record "Sales Header")
    var
        SalesLine: Record "Sales Line";
    begin
        SalesLine.SetRange("Document No.", SalesHeader."No.");
        SalesLine.SetRange("Document Type", SalesHeader."Document Type");
        SalesLine.SetRange(Type, SalesLine.Type::Item);
        if SalesLine.FindSet() then
            repeat
                if Get(SalesLine."No.") then begin
                    Quantity += SalesLine.Quantity;
                    Modify();
                end else begin
                    "Item No." := SalesLine."No.";
                    Quantity := SalesLine.Quantity;
                    Insert();
                end;
            until SalesLine.Next() = 0;
    end;
}

codeunit 50100 "PTE Get Items SalesHeader"
{
    [EventSubscriber(ObjectType::CodeUnit, Codeunit::"ForNAV TempTable",
        'OnFillTemporaryTable', '', false, false)]
    local procedure FillItemTotals(ReportID: Integer; ChildDataItemId: Text;
        ParentRecRef: RecordRef; var TempRecRef: RecordRef; var IsHandled: Boolean)
    var
        TempItemTotals: Record "PTE Item Totals" temporary;
        SalesHeader: Record "Sales Header";
    begin
        if IsHandled
            or (TempRecRef.Number <> Database::"PTE Item Totals")
            or (ParentRecRef.Number <> Database::"Sales Header")
        then
            exit;

        ParentRecRef.SetTable(SalesHeader);
        TempRecRef.SetTable(TempItemTotals);

        TempItemTotals.GetFromSalesHeader(SalesHeader);

        TempRecRef.Copy(TempItemTotals, true);
        IsHandled := true;
    end;
}
```

Guard order matters: check `IsHandled` first, then `TempRecRef.Number`, then optionally `ParentRecRef.Number` to scope to a specific parent — and set `IsHandled := true` only at the end, after the table is actually filled.

A ready-to-copy generic version of this is in `templates/event-subscriber-temptable.al`.

## Alternative: direct AL (`UseTemporary`) for reports you own

If you can modify the report object directly, declare the temp DataItem with `UseTemporary = true` and populate it in the parent DataItem's `OnAfterGetRecord`. No event subscriber needed — but you must still call FORNAV's `OnPreDataItem` hook on the temp DataItem so the Designer can introspect it. This is the single most commonly missed step in this pattern — without it, the layout silently can't see the data.

```al
dataitem(Header; "Sales Invoice Header")
{
    dataitem(TempItemSales; "PTE Item Sales")
    {
        UseTemporary = true;
        trigger OnPreDataItem()
        begin
            ReportForNav.OnPreDataItem('TempItemSales', TempItemSales);
        end;
    }

    trigger OnAfterGetRecord()
    begin
        GetTempData();
    end;
}
```

A ready-to-copy generic version is in `templates/direct-usetemporary-dataitem.al`.

## Scaffolding a new integration

When asked to create a new temp-table integration in a customer/partner AL repo:

1. Read that repo's `app.json` `idRanges` and scan existing object names for the project's naming prefix (e.g. `PTE`, or whatever convention is already in use) — never use the `ForNAV` prefix or FORNAV's own ID range (6188471–6189470), those are reserved for FORNAV's product source, not your extension.
2. Default to the event-subscriber pattern (`templates/event-subscriber-temptable.al`) unless the user says they own and want to modify the report object directly (`templates/direct-usetemporary-dataitem.al`).
3. Substitute the real table/field names and the real parent table into the template, keep the guard order, and write the table + codeunit as separate `.al` files following the repo's existing file-naming convention.
4. Tell the user the Designer-side step is still required: mark the DataItem/Record `Temporary` (+ `AutoPopulate` for DataItems) in the FORNAV Designer — this skill can't do that part for them.

## Reviewing existing FORNAV integration AL

Check for, in order:

- Subscribing to `OnForNAVFillTemporaryTableForNAV` (obsolete) instead of `OnFillTemporaryTable`.
- Missing or misordered guards — `IsHandled` not checked first, or set `true` before the table is actually filled.
- `UseTemporary` DataItems missing the `ReportForNav.OnPreDataItem(...)` call in their `OnPreDataItem` trigger.
- Event subscriber correctly scoped (`TempRecRef.Number` checked) but firing for the wrong report/parent because `ParentRecRef.Number` wasn't also checked when multiple reports share the same temp table name.

## Layout not picking up your data? Check activation priority

FORNAV resolves which layout a report uses with this priority cascade (highest wins):

1. Layout activated for the **current company and current user** (a BC-native per-user override).
2. Layout activated for the **current company** — this is what FORNAV's own "Activate" action sets.
3. A **global** layout activated with no company specified.
4. The report's **built-in** default layout.

If a layout change doesn't seem to apply, this is the first thing to check — a company-specific activation will silently override a global one regardless of which was edited more recently.
